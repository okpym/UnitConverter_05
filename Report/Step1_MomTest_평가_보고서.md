## 1) 사실 / 과거 / 구체성 평가

| 답변 | 평가 | 근거 |
|------|------|------|
| **언제 겪었나** | **양호** | "지난주 수요일", "23.6 inch", "방 여유 62 cm" — 시점·상황·숫자가 있음 |
| **어떤 방법** | **양호** | `23.6 × 2.54`, 결과 `59.944`, `62 − 59.944` — 실제 행동 순서가 드러남 |
| **불편한 점** | **보통** | `59.944` 반올림 등 구체 사례는 있으나, "단계가 늘면 헷갈린다"는 일부는 경험에서 나온 **해석**에 가까움 |
| **돈·시간** | **양호** | 유료 지출 없음, 5~7분 + 3분, 총 8~10분 — **commitment** 신호가 분명함 |
| **최근 노력** | **약함** | README 분석, OCP/SRP 정리, 기준값 계산 등 — **고객의 과거 행동**이 아니라 **만들 준비** 이야기로 이동 |

**전체:** 앞 4개 답변은 Mom Test 기준으로 **꽤 좋음**. 마지막 답변에서 **고객 인터뷰 → 제품/구현 준비 회고**로 전환됨.

## 2) 솔루션 섞임 지적

### 문제 없었던 구간 (Q1~Q4)
- 계산기·메모 앱 사용, 공식 직접 적용 — 당시 **실제로 한 일**이라 솔루션 피치가 아님.

### 섞인 구간 (Q5 — 최근 노력)
- `UnitConverter.py`, `README.md` 분석
- OCP, SRP, 테스트 체크리스트
- `meter:2.5` 출력 예시 대조

→ "고객이 최근에 뭘 했나?"가 아니라 **"내가 Unit Converter를 만들려고 뭘 했나?"**로 바뀜. Mom Test에서는 **아이디어 검증이 아니라 고객 생활 사실**을 물어야 하는데, 여기서 **솔루션·구현 맥락이 섞임**.

## 4) 지금까지 답변 요약 (불편·비용·마지막 행동)

### 불편
- 한 단위(23.6 inch)만 주어졌는데, 비교는 다른 단위(cm)로 해야 해 **계산을 나눠** 해야 함
- 쇼핑몰·계산기·메모를 **오가며** 원본/변환 숫자 구분이 어려움
- `59.944 cm`처럼 소수가 길면 **반올림 기준**마다 "약 2 cm 여유" 확신이 약함
- 다른 단위(meter, feet)로도 보고 싶을 때 **단위마다 공식을 다시** 써야 함

### 비용
- **돈:** 0원 (기존 무료 앱만 사용)
- **시간:** 첫 계산 5~7분 + 저녁 재검산 3분 ≈ **총 8~10분**
- 같은 변환을 **두 번** 반복한 것이 핵심 비용 신호

### 마지막 행동
- 인터뷰 직전(목요일): README·starter 코드 분석, 품질 요구 정리, 변환 비율 **손계산으로 기준값 확보**
- ⚠️ Mom Test 관점: 마지막 행동은 **고객의 문제 해결 행동**이 아니라 **개발자 준비 행동**
- 고객 쪽 마지막 행동은 여전히 **"책상 구매 망설이며 같은 계산을 저녁에 다시 함"**까지
